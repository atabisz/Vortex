# Project Research Summary

**Project:** Vortex Linux Support — v2.0 (Steam/Proton Detection, AppImage/deb Packaging, NXM Protocol)
**Domain:** Electron mod manager Linux porting milestone
**Researched:** 2026-03-31
**Confidence:** HIGH — all findings verified by direct codebase inspection

## Executive Summary

The v2.0 milestone is fundamentally a **completion and wiring milestone, not a greenfield build**.
The hard work was done in Phase 1: `Steam.ts`, `linux/steamPaths.ts`, `linux/proton.ts`, and the
entire `protocolRegistration/linux/` module are all committed and operational. Phase 2 closes a
handful of precise gaps — one platform-conditional path fix, one AppImage desktop-entry write, one
cold-start NXM buffer — plus two config file edits and a CI job addition. No new npm runtime packages
are needed at all.

The three feature tracks have radically different completion states going in. Steam/Proton detection
(STAM) is ~80% done and blocked on one correctness issue: `{mygames}` resolves to `~/Documents` on
Linux but Proton games store INI and save files inside the Wine prefix at
`compatdata/<appid>/pfx/drive_c/users/steamuser/Documents/My Games/`. Packaging (DIST) is a
two-line target change to `electron-builder.config.json` plus a new CI job. Protocol (PROT) is fully
implemented and needs integration testing plus one AppImage-specific desktop-entry write path that
was never coded for the packaged case.

The principal quality risk is the NXM cold-start bug: when the user clicks "Download with Manager"
while Vortex is closed, the spawned process consumes `--download` before the Redux store is ready
and silently drops it. This is a PROT blocker that affects perceived quality more than any other
single item. The fix is a buffered `pendingDownload` field in `Application.ts` — simple but easy to
overlook.

### Critical Gaps (actual coding work)

**Gap 1: `{mygames}` Wine prefix path resolution (STAM-04)**
`getVortexPath("documents")` returns `~/Documents` on Linux. For Proton games, INI/save files live
at `compatdata/<appid>/pfx/drive_c/users/steamuser/Documents/My Games/`. Add
`getMyGamesPath(steamEntry: ISteamEntry)` to `proton.ts`; call it from `gameSupport.ts` under a
`process.platform === 'linux' && steamEntry?.usesProton` guard. Critical: Wine prefix always uses
`steamuser` as the home directory name — never `os.userInfo().username`. Export
`PROTON_USERNAME = "steamuser"` as a named constant.

**Gap 2: Cold-start NXM buffering (PROT-01)**
When Vortex is closed and the user clicks "Download with Manager," the process starts fresh with
`--download nxm://...` in argv. `applyArguments()` is called only after `regularStart()` completes,
but the download URL is consumed before the Redux store is ready and silently dropped. Fix: store
`args.download` in a `private pendingDownload` field at startup; re-apply it in `onStoreReady`.

**Gap 3: AppImage desktop-entry gap (PROT-01 + DIST-01)**
For packaged AppImage builds, `nxm.ts` hits the `PACKAGE_DESKTOP_ID` path and calls `xdg-settings
set` — but no `.desktop` file is ever written to `~/.local/share/applications/` because
`ensureDevDesktopEntry()` is skipped for non-dev builds. `xdg-settings` silently assigns a
non-existent desktop ID; browser clicks on `nxm://` links do nothing. Fix: add
`ensureAppImageDesktopEntry()` gated on `process.env.APPIMAGE !== undefined`, writing
`~/.local/share/applications/com.nexusmods.vortex.desktop` with `Exec=$APPIMAGE --download %u`.
The `.deb` case is handled correctly by the package manager — no runtime write needed there.

### Critical Pitfalls

1. **`{mygames}` writes to wrong directory on Linux** (STAM-04 — silently blocks all Bethesda games)
   Prevention: `getMyGamesPath()` in `proton.ts`; use `PROTON_USERNAME = "steamuser"` constant;
   never construct Wine prefix paths with `os.userInfo().username`.

2. **Cold-start NXM URL silently dropped** (PROT-01 — kills "Download with Manager" for new users)
   Prevention: `pendingDownload` field in `Application.ts`; apply after Redux store `initialized`.

3. **AppImage `xdg-settings` registers non-existent desktop ID** (PROT-01/DIST-01)
   Prevention: `ensureAppImageDesktopEntry()` gated on `process.env.APPIMAGE`; write `.desktop`
   to `~/.local/share/applications/` at registration time.

4. **Flatpak + native Steam dual install — wrong library scanned** (STAM-02)
   Prevention: after resolving a Steam root, verify `steamapps/*.acf` files exist before treating
   it as the active installation; scan all valid roots and merge game lists.

**Also watch:** `mygamesPath()` async refactor must not break Windows callers (keep sync signature);
`latest-linux.yml` artifact name drift (set explicit `linux.artifactName`); NSIS scripts bundled
into Linux packages (move `"./nsis/**/*"` from top-level `extraResources` to `win.extraResources`).

## Implications for Roadmap

Tracks STAM and DIST are fully independent and can run in parallel. Track PROT depends on DIST
(needs a packaged AppImage to test the desktop-entry gap fix).

### Phase STAM: Steam/Proton Detection + INI Path Fix

**Rationale:** Foundation exists; this closes remaining correctness gaps. STAM-04 must land before
STAM-05 because Skyrim SE and Fallout 4 inherit the `{mygames}` fix — the audit is meaningless
without it.

**Delivers:**
- Flatpak Steam game detection validated and multi-root scan fixed (STAM-01/02)
- Proton prefix detection works for never-launched games via `oslist` ACF check (STAM-03)
- `{mygames}` resolves to correct Wine prefix location (STAM-04) — new code
- Top-4 game extensions (Skyrim SE, Fallout 4, Cyberpunk, Stardew Valley) confirmed on Linux (STAM-05)

**Files:** `proton.ts`, `gameSupport.ts`, `steamPaths.ts`, `Steam.ts`
**Avoids:** Pitfalls 1 and 4
**Research flag:** Skip — all patterns well-documented; implementation is additive to existing code.

---

### Phase DIST: AppImage + deb Packaging + CI

**Rationale:** Fully independent of STAM. Two config edits + one CI job. Must complete before PROT
validation because AppImage packaging is required to test packaged-build NXM registration.

**Delivers:**
- `vortex-setup-{version}.AppImage` and `vortex_{version}_amd64.deb` artifacts (DIST-01/02)
- `latest-linux.yml` generated and uploaded to GitHub releases (DIST-04)
- Linux packaging job in CI, parallel to Windows job (DIST-03)

**Files:** `electron-builder.config.json`, `package.yml`
**Avoids:** Auto-updater artifact name drift; NSIS scripts bundled into Linux packages
**Research flag:** Skip — electron-builder 24.x behavior verified; CI pattern mirrors existing
Windows job.

---

### Phase PROT: NXM Protocol Handler Wiring + Validation

**Rationale:** Depends on DIST (needs AppImage to test packaged-build registration). Code gaps
are small but require careful testing. PROT-02 SteamOS validation is the highest-risk item in
the entire milestone — Steam Browser behavior is unknown.

**Delivers:**
- AppImage NXM registration works without AppImageLauncher (Gap 3 fixed)
- Cold-start NXM URL correctly queues download (Gap 2 fixed)
- NXM handler validated on GNOME, KDE Plasma, and SteamOS Desktop Mode (PROT-01/02)
- `kbuildsycoca6` rebuild triggered on KDE Plasma after desktop DB update (PROT-02)

**Files:** `nxm.ts` (AppImage desktop-entry write), `Application.ts` (cold-start buffer)
**Avoids:** Pitfalls 2 and 3
**Research flag:** PROT-02 SteamOS Steam Browser behavior needs hardware validation. Flag as
"may defer Steam Browser support to v3.0" if hardware access is unavailable.

---

### Phase Ordering Rationale

- STAM and DIST share no files — fully parallelizable
- PROT code changes are small (two functions) but PROT testing requires an AppImage artifact,
  so DIST must be buildable first
- STAM-04 unlocks STAM-05 — game extension audit is meaningless without the `{mygames}` fix
- PROT-02 (SteamOS) must follow PROT-01 (standard Linux) — validate easy case first

### Research Flags

**Needs phase research:** Phase PROT — PROT-02 SteamOS. The Steam Deck's Discover overlay
(WebKit-based) may not delegate `nxm://` to `xdg-open`. No known fix. Requires hardware
validation; may need Nexus Mods web team coordination.

**Standard patterns (skip research):**
- Phase STAM — Proton Wine prefix structure is canonical; `steamuser` username is fixed across all
  Proton versions; `proton.ts` helpers already implement the required patterns.
- Phase DIST — electron-builder 24.x AppImage/deb behavior fully verified; CI pattern mirrors the
  existing Windows job in `package.yml`.

### Gaps to Address

- **AppImage auto-update on SteamOS (DIST-04):** `electron-updater` 4.2.0 AppImage replace step may
  fail on SteamOS immutable FS. Generating `latest-linux.yml` is still required; defer full
  auto-update validation to v3.0 if hardware test fails.
- **Steam Browser NXM link behavior (PROT-02):** No public documentation on whether SteamOS Discover
  overlay invokes `xdg-open` for custom protocol links. Requires Steam Deck hardware access.
- **`oslist` Proton pre-launch detection (STAM-03):** The `appmanifest_*.acf` `oslist` field is
  community-verified, not formally documented by Valve. Low risk — graceful fallback to `compatdata`
  directory check if absent.
- **Fallout 4 `winapi-bindings` shim scope (STAM-05):** The v1.0 webpack alias for `winapi-bindings`
  may not apply to the `extensions/games/game-fallout4` webpack context. Must confirm before
  declaring Fallout 4 unblocked on Linux.
