Modify the `reportUnsupported` method (around line 4504) to detect CSharpScript-specific
unsupported instructions on Linux and show a platform-appropriate message instead of the
generic "unimplemented functionality" dialog.

The C# fomod-installer emits unsupported instructions with `source === "CSharpScript"`
when a mod has a script.cs file but CSharpScriptType is not registered (which happens on
Linux due to the OS guard). These instructions flow through to `reportUnsupported` via
`instructionGroups.unsupported`.

Add early handling at the top of reportUnsupported, after the `length === 0` check:

```typescript
private reportUnsupported(
  api: IExtensionApi,
  unsupported: IInstruction[],
  archivePath: string,
) {
  if (unsupported.length === 0) {
    return;
  }

  // On Linux, C# script FOMADs emit a specific "CSharpScript" unsupported
  // instruction. This is a known platform limitation, not a bug — show a
  // clear message instead of the generic "unimplemented" dialog.
  const csharpUnsupported = unsupported.filter(
    (instr) => instr.source === "CSharpScript",
  );
  const otherUnsupported = unsupported.filter(
    (instr) => instr.source !== "CSharpScript",
  );

  if (csharpUnsupported.length > 0 && process.platform !== "win32") {
    api.sendNotification({
      type: "warning",
      message:
        "This mod uses a C# installer script that cannot run on Linux. " +
        "The mod was installed using basic file mapping. Some optional " +
        "components may be missing.",
    });
  }

  // Fall through to existing logic for any other unsupported instructions
  if (otherUnsupported.length === 0) {
    return;
  }
  const missing = otherUnsupported.map((instruction) => instruction.source);
  // ... rest of existing method unchanged ...
```

Key points:
- Filter unsupported instructions into CSharpScript-specific and other
- CSharpScript handling: `type: "warning"` notification (not "info") — it's a degraded
  install, user should know. No "Report" button — this isn't a bug.
- Guard with `process.platform !== "win32"` — Windows has full C# script support
- Fall through to existing generic handling for any non-CSharpScript unsupported instructions
- Update the `missing` variable to use `otherUnsupported` instead of `unsupported`

  <action>
In the copy instruction processing loop (around line 7922-7925), the source path goes
through `replaceAll("\\", "/")` which is now redundant because:
1. Parser10 in fomod-installer already normalizes all paths to forward slashes at XML
   parse time (via TextUtil.NormalizePath with alternateSeparators=true)
2. Plan 01 of this phase adds NormalizePath to the matchedFiles[0] source path too

Remove the replaceAll on the SOURCE only. Keep the destination replaceAll as
belt-and-suspenders since destination goes through path.join() which may reintroduce
backslashes on Windows.

Change from:
```typescript
const source = copy.source.replaceAll("\\", "/");
const destination = copy.destination.replaceAll("\\", "/");
```

To:
```typescript
const source = copy.source;
const destination = copy.destination.replaceAll("\\", "/");
```

This is a one-line change. The source value is passed directly to `resolvePathCase(tempPath, source, dirCache)` on the next line, which does its own case-insensitive path resolution.
