  <action>
    Start fresh: `git status --short` (must be empty) → `git checkout v8.0/config-bucket` → `git fetch fork` (if remote `fork` is configured locally; otherwise the inline SSH URL idiom works for ls-remote calls). Capture pre-rebase HEAD: `PRE_REBASE=$(git rev-parse HEAD); echo $PRE_REBASE` — record in `30-REBASE-NOTES.md` header.

    **Initialize 30-REBASE-NOTES.md** with header (timestamp, PRE_REBASE SHA, master target SHA, conflict-log table) BEFORE running rebase, so it's ready to append to during conflict resolution.

    **Run rebase**: `git rebase master`. For each conflict the rebase pauses on:

    1. `git status --short` — see which file(s) conflict.
    2. Inspect the file. Decide side per D-30-01:
        - **Default**: fork-side wins. Per RESEARCH.md Code Example 2, during `git rebase`, `--ours` = master (target), `--theirs` = v8.0 (replayed). So fork-side default → `git checkout --theirs <file>`.
        - **Exception**: `src/main/src/downloading/downloader.test.ts` (master Phase 25 SYNC-14 restore). Take master-side → `git checkout --ours <file>`.
        - **Bluebird trap**: if conflict file imports `Promise from "bluebird"`, do not pull in `:Promise<T>` annotations on async functions — TS1064. Manually edit if both sides have the annotation.
    3. `git add <file>` then continue inspection of any remaining conflicts.
    4. **Append entry to 30-REBASE-NOTES.md**: file path, side picked (`--ours` or `--theirs`), one-sentence rationale (e.g., "fork-side default per D-30-01" or "master-side restoration of upstream test file per D-30-01 exception").
    5. **api.d.ts drift**: if `packages/vortex-api/lib/api.d.ts` shows up modified (regenerated as side-effect of any commit's typecheck during rebase), discard it: `git checkout HEAD -- packages/vortex-api/lib/api.d.ts` per Phase 28/29 chore-pattern.
    6. `git rebase --continue`.

    **If a single commit has so many conflicts it's not coherent to resolve atomically**: STOP — do not silently squash or drop. Surface to the user with: the conflicting commit's SHA + subject, the conflict files, your suspicion (pure churn, duplicates a master commit, etc.), and the proposed action (squash into neighbour / drop / keep-and-resolve). Wait for explicit approval before `git rebase --edit-todo`. Once approved, document each squash/drop in 30-REBASE-NOTES.md with: the original commit SHA, the rationale, AND (for drops) the master commit it was redundant against (if any). No silent squashes; no silent drops.

    **Post-rebase verification (BEFORE pushing):**

    1. `bash .planning/milestones/v8.0/scripts/grep-checkpoint.sh` — must exit 0 with all 16 gates green.
    2. `pnpm typecheck` — must exit 0 (api.d.ts may regenerate; discard with `git checkout HEAD -- packages/vortex-api/lib/api.d.ts` if it does).
    3. `git log --oneline master..v8.0/config-bucket | wc -l` — record commit count (expect ~374, possibly ±a few if conflicts forced squashes).
    4. `git merge-base master v8.0/config-bucket` — must equal `git rev-parse master` (proves linear FF-able chain).

    Append final `## Post-rebase verification` section to 30-REBASE-NOTES.md with all four results pasted verbatim. Do NOT push or commit — Task 1-2 handles that.

    Casual voice on rationale entries.
